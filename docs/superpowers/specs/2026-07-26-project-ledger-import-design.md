## 生产数据保留与清理边界

生产数据库在实施前必须创建带时间戳的 SQLite 完整备份，并备份 `uploads/` 目录。

以下数据不得删除、重置或覆盖：

- 公司

- 工资与薪资结算

## 方案选择

采用“完整结构化导入”方案，不采用将二级分类塞入现有凭证类型、将其他字段拼接进备注的扁平方案，也不另建与凭证模块并行的第二套账务系统。

现有项目凭证模块继续作为唯一入口，但其数据模型升级为完整的项目财务明细模型。旧字段在数据库迁移阶段保留兼容，所有新写入统一走结构化字段。

## 数据模型

### 分类

`expense_categories` 从单层分类升级为树形分类：

- `id`
- `name`
- `parent_id`：一级分类为空，二级分类指向一级分类
- `transaction_scope`：支出、收入、资金往来或通用
- `sort_order`
- `is_active`
- `created_at`

分类名称在同一父分类下唯一。一级和二级分类均可停用；被财务明细引用的分类不能直接删除。分类迁移必须在单个事务中同步更新引用并写入审计日志。

源账套正式明细与待补录清单合计使用 12 个一级分类和 59 个二级分类；其中“材料费 / 干拌料及砂浆”只出现在缺少金额的待补录事项中，也必须进入生产分类字典。原有 7 个演示分类在删除演示凭证后停用，避免以后再次出现在录入候选中。

### 财务明细

继续使用 `vouchers` 作为正式财务明细表，保留现有主键和项目关联，并新增：

- `source_record_id`：源账套记录编号，全局唯一
- `transaction_type`：支出、冲减支出、收入、资金往来
- `category_id`：指向二级分类
- `handler_name`：经办或垫付人
- `payment_status`：四种已确认状态之一
- `payment_date`
- `payment_notes`
- `review_status`：已确认或待复核
- `classification_confidence`：高、中、低
- `source_filename`
- `source_sheet`
- `source_row`
- `original_notes`

金额保持正数，财务方向由 `transaction_type` 决定。项目净支出按“支出 - 冲减支出”计算，收入和资金往来不得混入项目成本。

`source_record_id` 建立唯一索引，保证账套重复导入时不会产生重复明细。

旧的 `voucher_type` 字段在本次迁移中保留为兼容字段，新记录写入二级分类名称。所有统计、筛选和校验以 `category_id` 为准；待页面和导出全部迁移后再评估移除旧字段，本次不做破坏性删列。

### 待补录事项

新增 `ledger_pending_items` 表保存 276 条缺少金额的记录：

- 项目
- 发生日期
- 事项摘要
- 建议一级/二级分类
- 经办或垫付人
- 支付说明
- 来源文件、工作表、原始行号
- 待确认问题
- 状态：待补录、已转正式明细、已忽略
- 转换后的财务明细 ID

待补录事项不进入项目成本、收入或资金往来统计。补齐金额并确认后，由服务层在单个事务中创建正式明细并标记来源事项已转换。

## 项目导入规则

导入前删除已确认的演示项目相关数据，然后创建 6 个真实项目：

- 项目名称严格使用账套中的名称
- 所属公司统一使用生产库中的主公司
- 开始日期使用该项目最早正式明细日期
- 状态默认“进行中”
- 负责人、结束日期不从账目内容推断，保持为空
- 备注记录导入来源、账目期间和导入时间

账套列映射：

| 源字段 | 系统字段/处理 |
|---|---|
| 记录编号 | `source_record_id` |
| 项目名称 | 项目精确匹配 |
| 发生日期 | `voucher_date` |
| 收支类型 | `transaction_type` |
| 一级/二级分类 | 二级 `category_id` 及其父分类 |
| 事项摘要 | `notes` |
| 金额 | `amount` |
| 经办/垫付人 | `handler_name` |
| 支付状态 | `payment_status` |
| 支付日期 | `payment_date` |
| 支付/报销说明 | `payment_notes` |
| 备注 | `original_notes` |
| 分类置信度 | `classification_confidence` |
| 来源文件/工作表/行号 | 对应来源追溯字段 |

“有金额待复核”清单通过来源文件、工作表和原始行号与正式明细匹配，匹配到的 483 条记录写入 `review_status = '待复核'`。缺少金额的 276 条记录只写入 `ledger_pending_items`。

## 导入服务

实现可重复使用的标准账套导入服务和命令行入口，支持：

- ZIP 或单个 XLSX 输入
- 结构与必需工作表校验
- 只读预检（dry run）
- 项目、分类、正式明细、待补录事项数量和金额汇总
- 全量事务导入
- 来源编号幂等去重
- 错误定位到文件、工作表和行号
- 导入审计事件

任何文件结构错误、项目名称不一致、分类不存在、日期无效或金额无效，都必须在写入前阻止导入。正式导入发生异常时整批回滚，不能留下半个项目或部分分类。

## 页面与交互

项目账套页面增加以下汇总指标：

- 支出原额
- 冲减支出
- 项目净支出
- 收入
- 资金往来
- 未支付金额
- 待复核数量
- 待补录数量

明细列表增加收支类型、一级分类、二级分类、经办人、付款状态和复核状态，并提供日期、收支类型、一级分类、二级分类、付款状态、复核状态筛选。

分类管理页面改为一级/二级树形管理。使用中的分类只允许停用或迁移，不允许直接删除。录入和编辑财务明细时，二级分类候选必须由所选一级分类动态过滤。

新增“待补录”视图，用于补齐 276 条缺少金额的事项并转换为正式明细。483 条已有金额的待复核明细在正式明细列表中集中筛选和修正。

页面继续使用现有 Flask/Jinja2 和本项目已有的交互、图标、色彩及紧凑后台布局，不引入新的前端框架。

## 统计与导出

看板、项目账套汇总和 Excel 导出统一使用以下口径：

- 项目净支出 = 支出 - 冲减支出
- 收入单独列示
- 资金往来单独列示
- 待补录事项不计入任何金额
- 作废明细不计入金额和笔数
- 未支付金额只统计支出与冲减支出相关的未结状态

项目账套导出包含完整来源和复核字段，并进行 Excel 公式注入转义。汇总结果必须与源账套逐项目、逐收支类型对平。

## 测试策略

实施使用测试驱动：

1. 数据库迁移测试：旧库升级后新增字段、索引、分类层级和待补录表正确，已有保留数据不变。
2. 解析测试：6 个源账套的字段、日期、分类、付款状态和来源信息解析正确。
3. 导入测试：正式明细、待复核和待补录数量准确，异常整批回滚。
4. 幂等测试：同一压缩包重复导入不会增加记录。
5. 统计测试：支出、冲减、净支出、收入和资金往来口径正确。
6. 页面测试：筛选、编辑、分类联动、待补录转换、分类停用与迁移正确。
7. 回归测试：登录、人员、资质、考勤、工资、合同、附件、四类导出及安全修复继续通过。

## 上线流程

1. 在本地完成迁移、导入和页面测试。
2. 对生产数据库与上传目录创建新的时间戳备份。
3. 停止 `cam.service`，避免迁移期间产生并发写入。
4. 发布经过测试的代码，并运行数据库迁移。
5. 以 dry run 对生产备份副本执行账套预检，核对数量和金额。
6. 在生产库单事务执行演示项目清理、分类初始化和账套导入。
7. 启动服务并运行健康检查和页面冒烟测试。
8. 按项目核对明细数、待复核数、待补录数和财务总额。
9. 修改 Nginx TLS/上传限制，校验配置后平滑重载。

如果验证失败，停止服务并恢复本次实施前的数据库、上传目录和代码备份。
